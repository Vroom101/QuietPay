# Attack log (backend audit)

| Id | Round | Angle | Finding | Severity | Status |
|---|---|---|---|---|---|
| F13 | B1 audit | Front-running of the agent's signed EIP-3009 authorization | A third party submitting the authorization first made our transfer revert; `finish()` marked the payment `failed` although the payee was paid, so the payer paid and got nothing and could not retry (unique payer+nonce). Same outcome if the foreign tx landed before verify (`payment_replayed`) or before our send (simulation failed). | High (payer misled) | Fixed. Reverted/failed-to-send attempts now call `chain.findExternalSettlement`; a plain `transferWithAuthorization` to the token paying exactly this payer, payee, amount and nonce, 2+ blocks deep, settles the row with the foreign hash (`settlement_source=external`, our gas spend kept). Shallow: stays pending. Cancelled: failed. Used but unbindable (forwarder/multicall, cancel without event): `unresolved`, never delivered. Tests: 11 unit (front-run.test.ts) + real-chain anvil front-run (anvil-front-run.test.ts, fails on the old code with `failed`). |

Residual (Low, documented): a payload observed by a third party can be redeemed for any resource with the same price and payee (the signature does not cover the resource). USDT blacklist or fund freezing after payment is out of scope. A foreign tx that reaches the token only through a forwarder or multicall is parked as `unresolved` for review (no trace-based binding yet).

| R16 | B1 audit | Reorg after a receipt | The relayer settled on the first receipt (1 confirmation); a block reorganised away after payment.settled would leave the merchant unpaid. | Medium | Fixed (opt-in): SETTLE_CONFIRMATIONS (default 1 = unchanged; set higher on any chain that can reorg). A shallow receipt leaves the order pending; a vanished receipt never settles. 3 tests in audit-b2.test.ts. |

| M1 | B2.4 matrix | Wildcard CORS plus `authorization` on authenticated routes | Every relayer and facilitator route, including merchant and operator ones, answered `access-control-allow-origin: *` and allowed the `authorization` header, so any web page holding a key could call them from a browser. | Medium | Fixed. Wildcard CORS only on the public routes (health, order status, relay/pay, /supported). Authenticated routes answer only origins listed in `CORS_ORIGINS` (echoed with `Vary: Origin`); default none. |
| M2 | B2.4 matrix | Default 404 echoed the requested method and path | Fastify's built-in 404 reflected attacker-controlled text in all three services. | Low | Fixed. Fixed `{error:{code:"not_found"}}` body everywhere. |
| M3 | B2.4 matrix | Facilitator turned every error into 400 | Oversized bodies returned 400 instead of 413 and bad content types lost their 415. | Low | Fixed. Fastify 4xx statuses are preserved with fixed codes (`payload_too_large`, `unsupported_media_type`, `invalid_payload`). |
| M4 | B2.4 matrix | No request timeouts, paid API had the 1 MiB default body limit | Slow clients could hold sockets open; the paid API accepted large bodies on routes that read none. | Low | Fixed. `requestTimeout` 30 s, `headersTimeout` 15 s, `connectionTimeout` 60 s on both apps; paid API body limit 16 KiB, fixed error handler. |
